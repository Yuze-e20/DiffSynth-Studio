# 评测指标

供 control_scale 之类的配比搜索用，替代肉眼判断。不改 diffsynth 框架，只 import 它。

定稿的三个指标（2026-10-27 暂定）：线稿一致性 `lineart_boundary_f.py`、色彩保持
`color_consistency.py`、流畅性 `vbench_flicker.py`（直接调 VBench 的 API）。三个文件的默认值就是
现在在用的那一档，跑的时候不用再带参数。`flow_warp_error.py` 留着当流畅性的光流对照，不是默认项，
它和 VBench 在 t 轴上不一致，原因见下面两节。**不要加权合成总分**，三个分数分开看。

## Boundary F-score（带空间容差的线稿一致性）

`lineart_boundary_f.py` — 对生成视频再跑一次 `video_lineart` 提线稿，和真实视频的线稿比。

```bash
cd DiffSynth-Studio
python -m metrics.lineart_boundary_f \
    data/test_Pixabay100/13/13.mp4 \
    data/test_Pixabay100/13/13_nf345_ctx1g_s20_u08_t06_imp.mp4 \
    --compare-dir metrics/compare/13

# 线稿已经提好了就跳过提取
python -m metrics.lineart_boundary_f 真实线稿.mp4 动漫线稿.mp4 --lineart-given
```

关键参数：`--tolerance`（默认 1.5 像素）、`--strict`（默认 1.0，Otsu 阈值倍数）、
`--stride`（隔帧评测，调参时用 20~40 快很多）。

容差是欧氏距离，所以默认的 τ=1.5 收的是**八邻域**：上下左右距离 1，对角 1.414，都算命中，
距离 2 的不算。要只收四邻域就用 τ=1。

### 三个设计点

**对齐。** 控制线稿是 1920x1080@30，输出是 1344x768@24，1.6% 的宽高比差异在 2 像素容差
下会直接盖掉真实差异。所以参考轨先过 diffsynth 自己的 `crop_and_resize`，帧映射也用推理
时那套 `round(k*src_fps/24)`（`read_video_audio` 的逻辑）。这两个都是 import 来的，不是
重写的，保证落在生成时看到的同一批像素上。

**二值化。** 线稿是灰度的，Otsu 取阈值。阈值对**整段视频只取一次**（采样 24 帧汇总）：
逐帧 Otsu 会让阈值跟着内容飘，一帧只有淡线时也会被拉出和繁忙帧一样多的边缘，分数就
为了跟生成质量无关的原因而波动。两条轨各取自己的阈值 — 实拍帧比赛璐珞繁忙，强行共用一个
阈值等于在量这个偏移。`--strict` 是阈值倍数，>1 只保留较强的线。实测扫过 1.0~2.5（见
`compare/strict_sweep/`，每档一个左实拍|右动漫的并排二值视频），画面上差别很小，所以默认
就用 Otsu 自己的切点、不再加倍数。**只有评测走二值化，喂给 ControlNet 的仍然是原始灰度轨。**

**容差。** 用精确的欧氏距离变换（`distance_transform_edt`），不是膨胀近似。预测边缘点在
参考距离图上读数 <= tolerance 就算命中，反向同理 —— 这个不对称性才让 F1 有意义：什么都不画
recall 为 0，画满整屏 precision 趋近 0。

### 实测（clip 13，strict 1.3，2px —— 旧默认下测的区分度对照）

| 参考 | F1 | precision | recall |
|---|---|---|---|
| 配对的真实线稿 | 0.694 | 0.726 | 0.664 |
| 故意换成 clip 45 的线稿 | 0.104 | 0.060 | 0.429 |

错配只剩 0.10，说明指标确实在量内容一致性而不是在量「两张图都有线」。

### compare 目录

`--compare-dir` 会写四个视频，都在输出的 1344x768 网格上、24fps，方便逐帧对位看：

- `real_lineart.mp4` / `anime_lineart.mp4` — 对齐后的灰度线稿
- `real_lineart_binary.mp4` / `anime_lineart_binary.mp4` — 二值化之后的（也就是真正参与打分的）

## 分辨率对齐（三个指标共用）

源视频 1920x1080@30（或 23.98），输出 1344x768@24。三个指标都走 `lineart_boundary_f.read_aligned`：
空间上过 diffsynth 自己的 `crop_and_resize`（import 的，不是重写），时间上用推理时那套
`round(k*src_fps/24)` 帧映射。所以参考轨落在生成时实际看到的那批像素上，不存在拉伸或错帧。
实测两支片子对齐后都是 `(768, 1344, 3)`、帧数 603/603 和 961/961。

## 色彩保持（CIEDE2000，去掉亮度维）

`color_consistency.py` — a/b 两维算 CIEDE2000，L 强制常数。

```bash
python -m metrics.color_consistency 真实.mp4 生成.mp4 --stride 20
python -m metrics.color_consistency 真实.mp4 生成.mp4 --sigma 0   # 关掉高斯
```

**去 L 是实现无关的。** dL=0 时 CIEDE2000 的亮度项自己消掉（S_L 乘零），所以两边都设 L=50、
都设 L=20、或者照抄参考的 L，结果完全一样。三渲二本来就要压平渐变、拉高对比，量亮度等于在罚
我们想要的效果。

**用 CIEDE2000 不用 Lab MSE。** 这俩不是两种方法：Lab 欧氏距离就是 ΔE76，Lab 三通道 MSE×3
等于 mean(ΔE76²)。ΔE76 是 CIEDE2000 的前身，会过罚高饱和区 —— 同样的 ab 偏移它到处都报
8.49，CIEDE2000 在中性灰上报 8.70、在饱和黄上报 3.75。赛璐珞大面积是饱和色块，这个差别不能忽略。

**a/b 上的高斯（σ=15）。** 黑色轮廓是 a=b=0 也就是中性色，在 Lab 里和灰色重合，轮廓错一个像素
就被记成整个色差。模糊 a/b 让周围颜色扩散进来稀释掉它 —— 和色度二次采样同一个道理。这是频率
分离不是放水：模糊会压低匹配的 ΔE 而错配的几乎不动，注入的低频故障（全局染色、局部换色块、
降饱和 30%）都不会被盖掉。

σ 的代价是实测过的，所以不要无脑往大调：

| σ | c13 匹配/错配/ratio | c45 匹配/错配/ratio | 局部故障惩罚 | a 通道帧内 std |
|---|---|---|---|---|
| 0 | 6.81 / 26.1 / 3.83 | 6.06 / 20.7 / 3.42 | 0.476 | 8.61 |
| 3 | 5.48 / 26.4 / 4.82 | 6.05 / 20.5 / 3.40 | 0.495 | 7.75 |
| 12 | 4.26 / 26.4 / 6.20 | 5.85 / 20.1 / **3.44** | 0.484 | 6.81 |
| 15 | — | — | — | — |
| 24 | 3.78 / 26.4 / 6.97 | 5.82 / 19.7 / 3.39 | 0.447 | 6.24 |
| 48 | 3.47 / 26.2 / 7.54 | 5.88 / 19.2 / 3.26 | 0.345 | 5.53 |
| 64 | 3.37 / 26.1 / 7.76 | 5.92 / 18.9 / 3.20 | — | — |

c13 的 ratio 一路涨到 σ64 都不停，但涨幅全来自匹配项变小（错配项钉在 26.4 不动），也就是真实
差异也被抹掉了；c45 在 σ12~14 见顶然后回落。两支片子没有共同的涨停点，σ=15 落在 c45 的峰上。
再往大走有两个量化代价：128x128 色块 R/B 互换这个局部故障的惩罚 σ12 前稳定在 0.48，σ24 掉到
0.447、σ48 只剩 0.345；a 通道帧内标准差同区间从 8.61 掉到 5.53，指标退化成在比整帧平均色。

ab 直方图交集是互补项，故意不加高斯：ΔE2000 是逐像素的、在意颜色放在哪，直方图完全不管位置、
只问色板对不对。色板对但位置错的结果在直方图上高分、在 ΔE 上低分，两个一起看才知道是哪种坏。

实测（stride 40）：

| | 匹配 ΔE2000 | 直方图交集 |
|---|---|---|
| clip 13 | 3.975 (sd 0.281) | 0.6492 |
| clip 45 | 5.514 (sd 0.547) | 0.3361 |
| 错配（45 源 vs 13 生成） | 26.029 | 0.0555 |

## 流畅性的光流对照（`flow_warp_error.py`，非默认）

`flow_warp_error.py` — 沿运动轨迹取三帧 (t-1, t, t+1)，把两个邻帧都 warp 到第 t 帧上。

```bash
python -m metrics.flow_warp_error 真实.mp4 生成.mp4 --stride 30
python -m metrics.flow_warp_error 真实.mp4 生成.mp4 --compare-dir metrics/compare/13_flow
```

**主指标是 `flicker`，不是原始 Pixel-MSE。** 原始 warp error 在这个任务上会选错配置，两个原因都是
实测出来的，不是推测：

- **锐度混淆。** 平方残差随局部对比度缩放，一条清晰赛璐珞边线偏半个像素的代价远大于照片式渐变
  偏同样距离。t 从 0.5 涨到 1.0，梯度能量从 7.069 掉到 5.701，于是原始误差跟着掉——掉的原因和
  稳定性无关。除以局部亮度 std（9×9 窗，下限 4.0）后方向就翻过来了。
- **漂移和闪烁混在一起。** 单个 t→t+1 残差分不开缓慢漂移和逐帧交替。沿轨迹的时间二阶差分
  `2*I_t - warp(I_{t-1}) - warp(I_{t+1})` 把光流能解释的运动、以及沿轨迹的任何线性变化都消掉，
  只剩交替。

u0.8 那一行（肉眼不同意原始排序的那行）：

| config | warp_mse | norm_mse | 二阶原始 | **flicker** | 梯度能量 |
|---|---|---|---|---|---|
| t0.5 | 10.755 | 0.0252 | 25.315 | 0.0539 | 7.314 |
| t0.6 | 8.865 | **0.0225** | 21.183 | 0.0507 | 7.222 |
| t0.7 | 7.795 | 0.0226 | 18.645 | **0.0501** | 6.885 |
| t0.8 | 7.193 | 0.0237 | 16.709 | 0.0520 | 6.546 |
| t0.9 | 6.868 | 0.0252 | 15.317 | 0.0547 | 6.134 |
| t1.0 | **6.831** | 0.0282 | **14.976** | 0.0597 | 5.804 |

原始二阶差分单调偏向 t1.0（画面已经在闪了），归一化后在 t0.7 见底、t1.0 比 t0.5 还差，和肉眼
以及线稿 F1 的最优区一致。

**`pair_flow` 必须返回 a->b 那一侧的流场。** `flow_warp` 算的是 `out[p] = img[p + flow[p]]`，
位移要以 frame_a 的像素为索引、指向这块内容在 frame_b 里的位置，也就是 `model(a, b)`。返回
`model(b, a)` 的话小运动下近似是它的相反数，位移朝反方向走。这个 bug 不会报错，只会被数值吸收
掉：源视频 warp 到自己身上，正确流场残差 1.42、反向的 5.49，而且这个差值和运动幅度的相关系数是
0.83——所以反向流场读起来像"只要有东西动就不稳"，看着像个合理的指标而不像 bug。

**两个温度指标的全局最优都是"什么都不做"。** 源视频自己打分 warp error 1.42，比最好的生成配置
6.83 低得多，所以这个数单独不能选配置，只能在一批风格化输出之间排序。源视频输的只在风格轴上：
平坦区占比 0.336，而所有生成配置都在 0.40~0.42。

**clip 13 本身是近静态场景**，相邻帧 MAE 只有 0.54/255（gap 2/5/20 分别是 0.82/1.80/3.62，没有
重复帧），光流 99 分位 0.6px、最大 ~4px、均值 0.03px（大部分画面是背景）。所以这一片的 warp
residual 主要在量生成自身的抖动，而不是运动补偿的难度。

Rerender_A_Video 里**没有现成的评测代码**，`flow/flow_utils.py` 里是生成时用的组件
（`flow_warp`、`forward_backward_consistency_check`、`FlowCalc`），指标本身要自己拼。它的
gmflow 权重也没下载（`models/` 目录不存在、HF 在这台机上连不通），所以光流换成 torchvision 的
RAFT-large（C_T_SKHT_V2，权重能直接拿到）。前后一致性检查沿用 Rerender 那套 UnFlow 参数
（alpha=0.01, beta=0.5）。

**光流从源视频估，不从生成视频估。** 在生成帧上估光流会让闪烁藏起来：光流器把闪烁吸收进一个
错的运动场，残差反而变小。源视频是运动的真值，也正是生成时的条件，所以搜配比时光流是所有配置
共享的，变的只有被 warp 的像素。

注入故障对照（clip 13，u0.8 t0.8 为基线，stride 20，全部在 1344×768 网格上重写后再打分）：

| | **flicker** | 倍数 | Pixel-MSE | 倍数 |
|---|---|---|---|---|
| 真实源视频（下界参考） | 0.0279 | 0.54× | 1.318 | 0.18× |
| 生成视频（基线） | **0.0520** | 1× | **7.193** | 1× |
| 加 sd8 逐帧噪声 | 2.0476 | 39× | 75.3 | 10× |
| 3px 隔帧抖动 | 13.1954 | 254× | 1112.5 | 155× |
| 帧序打乱 | 4.2427 | 82× | 305.2 | 42× |

**除以局部对比度没有牺牲动态范围，反而拉开了**：每个故障对基线的倍数都比原始 MSE 大 2~4 倍。
隔帧抖动那一行最关键——它是纯交替、没有漂移，打到基线的 254 倍，说明二阶差分在干它该干的事。

**注意这几行注入故障对流场方向不敏感**，所以它们验证不了方向 bug：3px 抖动和随机换帧远大于
亚像素位移误差，修方向前后分别是 13.182 / 13.195 和 4.221 / 4.243，几乎没动。能发现方向错的是
源视频那一行——修完它从 5.042 掉到 1.318，而基线只从 10.911 掉到 7.193。这个不对称正是方向修
对了的表现：源视频在自己的运动场下是自洽的，位移方向一改残差几乎全部收回；生成视频的残差主要
是它自己的抖动，warp 再准也去不掉。

clip 45 有效像素只剩 64%（clip 13 是 0.967），是黑背景让光流前后一致性大面积失败。

**有效像素占比要一起看。** 运动场不可靠的地方（去遮挡、出画、前后向光流互相矛盾）残差不说明
闪烁，所以被剔掉；遮挡情况不同的两个配置并不是在同一批像素上打分。二阶项要求两个邻帧的掩码
同时有效，一阶项只用后向那一对。

`score_pair` 的网格取自 `generated`，所以传进来的 `flow_cache` 如果是别的分辨率上建的，会直接
报错而不是拿错的光流场去 warp（1920×1080 的源视频和 1344×768 的生成就是这种情况）。

`--compare-dir` 写一个 `flicker_residual.mp4`：归一化二阶残差的灰度热图，被剔掉的像素涂黑。

扫配比时把同一个 dict 传给 `score_pair(..., flow_cache=cache)`：光流只依赖源视频，36 个配置共用
一份。缓存的 key 是中心帧下标，所以换了源视频、stride 或分辨率就要换 dict。

## 流畅性（`vbench_flicker.py`，默认）

定稿用这个，理由是实现简洁：一次函数调用，不用光流、不用跑 RAFT、没有缓存和网格对齐的坑。代价
写在下面——它在 t 轴上选 t0.9，和肉眼以及 `flow_warp_error.py` 的 t0.7 不一致，所以**拿它排 union
那一档（u）可以，排自训那一档（t）时要留心**。

VBench 的 `temporal_flickering` 全部计算就是 `(255 - mean|I_t - I_{t+1}|)/255`，没有光流、没有
运动补偿、没有遮挡掩码，docstring 自己写着 "please ensure the video is static"，benchmark 里也
只跑在被 `static_filter.py` 筛成静态的那批 prompt 上。

```bash
python -m metrics.vbench_flicker 生成.mp4
python -m metrics.vbench_flicker --grid 13                      # 整个 u/t 网格
python -m metrics.vbench_flicker --grid 13 --row u08 --source .../13/13.mp4
```

默认报的就是 VBench 自己的分（`score()`，直接调它的 `cal_score`，它自己的 reader，不重采样）。
`--aligned` 那一列是我加的：用 VBench 自己的 `mae_seq`/`calculate_mae`，但喂我们 `read_aligned` 的帧，这样源视频
（1920×1080@30fps/753f）和生成（1344×768@24fps/603f）才在同一个网格上。生成那几行两者五位小数
一致（本来就在目标网格上），只有源视频那行差（0.99775 vs 0.99753）。

| config | vb_raw | MAE | 我们的 flicker | 梯度能量 |
|---|---|---|---|---|
| SOURCE | 0.99775 | 0.629 | 0.0279 | 7.900 |
| t0.5 | 0.99612 | 0.989 | 0.0539 | 7.314 |
| t0.6 | 0.99620 | 0.970 | 0.0507 | 7.222 |
| t0.7 | 0.99638 | 0.922 | **0.0501** | 6.885 |
| t0.8 | 0.99649 | 0.896 | 0.0520 | 6.546 |
| t0.9 | **0.99655** | 0.881 | 0.0547 | 6.134 |
| t1.0 | 0.99653 | 0.884 | 0.0597 | 5.804 |

**它站在原始列那边，不站在 flicker 这边——这就是选它要付的代价。** 相关系数：原始二阶差分 +0.977、原始 MSE
+0.961、**梯度能量 +0.923**、flicker −0.438。它选 t0.9，flicker 选 t0.7。那个 +0.923 就是全部
原因——没有对比度归一化，画面越平相邻帧差就越小，它把这个读成稳定，正是我们要修的那个混淆。

**两点注意：**（1）动态范围几乎不够用，六个配置全挤在 0.9961~0.9966，MAE 上 11.7% 的差被压进
小数第四位——VBench 是用来区分不同视频生成模型的，不是区分同一模型的两档 control_scale。
（2）它同样有 identity 最优的毛病（源 0.99775 > 最好的生成 0.99655），只是在那个精度下看不见。

好的一面：这是一个完全独立、不用光流的实现，和我们的原始列相关 +0.96/+0.98，等于交叉验证了
算术和流场方向修复；分歧只落在对比度归一化这一件事上。两边不一致的时候，跑一遍
`flow_warp_error.py` 看是不是又是"平被读成稳"。

安装注意：`pip install --no-deps vbench` 再单独装 `decord`。VBench 0.1.5 钉死
`transformers==4.33.2`、`timm<=1.0.12`，直接装会把 env 里的降级，大概会弄坏 diffsynth。

## 三个指标都只能同片内比

clip 13 密集（线稿密度 ~20%，动漫画得更少，precision > recall），clip 45 是稀疏黑背景
（~2~3%，动漫多画 ~40%，precision < recall，逐帧 sd 高一个数量级），色彩和光流指标上也是
一样的量级差（直方图交集 0.65 vs 0.34，有效像素 0.97 vs 0.64）。聚合要用片内排名，
不要跨片平均。
